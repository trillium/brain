# Runbook: create a store, roll a binary out, prove every machine has it

Read it in the binary with `brain runbook stores-and-deploy`; this file is the
source that is embedded (`docs/brain/runbooks.go`).

Three jobs, in order: (1) create a store on the machine that hosts the database,
(2) put a brain binary that knows about it on the other machines, (3) prove every
machine has the store configured. Nothing here is automated; each step names the
command and the output that says it worked. Background:
[`STORE_REGISTRY.md`](STORE_REGISTRY.md), per-machine plan:
[`STORE_REGISTRY_DEPLOY.md`](STORE_REGISTRY_DEPLOY.md), client mode:
[`REMOTE.md`](REMOTE.md).

Legend: **[code]** = checked against this repository's source. **[observed]** =
seen by hand on 2026-10-22 and not provable from this repository. **[unverified]**
= could not be checked from here; confirm it on the machine before relying on it.

## 0. Before you start

* Know which machine hosts the database (the brain host). Today that is mini0
  **[observed]**; `brain host status` on any machine says what it believes.
* Know which machines are in the fleet roster: `~/.config/brain/fleet.yaml`, else
  the default `mini0`, `mini1`, `macbook` **[code]** (`defaultFleetRoster`).
  mini2, mini3 and lnx are not in the default roster; the roster file or
  `--machines` adds them **[code]**. Whether the deploy user can ssh to each is
  **[unverified]** until step 6 proves it.
* The store registry must be adopted in the database, or `create` only prints a
  note and other machines will not learn of the store **[code]**
  (`brain stores epoch` shows the database epoch; `brain stores reconcile`
  adopts it, see the deploy plan).

## 1. Create the store (on the host machine only)

Run on the machine that hosts the database, as the user that owns the brain
wrappers there.

```sh
brain stores create <name>
```

What it needs **[code]**:

* **Run it on the database host.** It provisions the store with a direct SQL
  connection to the shared Dolt server (shared-server mode is on when the `brain`
  wrapper exports `BEADS_DOLT_SERVER_MODE=1`, host and port default to
  `127.0.0.1:3307`). On a client machine (`~/.config/brain/remote.yaml`) the
  command is forwarded to the host over ssh instead, so the effect is the same
  but the host does the work.
* **A database login with create rights.** Since PR 55 the connection uses the
  configured login: user from `BEADS_DOLT_SERVER_USER` (default `root`), password
  from `BEADS_DOLT_PASSWORD`, else the matching `[host:port]` section of the beads
  credentials file (`~/.config/beads/credentials`). Before PR 55 it always
  connected as passwordless `root` and failed with `Error 1045` on a machine
  already moved to the `brain_app` login.
* The name is lowercase, no spaces, dots or slashes; the default directory is
  `~/data/<name>`.

Verify:

```sh
brain stores epoch                 # database epoch went up by one
brain stores list | grep -w <name> # the store is listed on this machine
<name> list                        # the new wrapper reads the empty store
brain stores doctor --fleet --machines <host-name>
```

Expected: `create` prints `Created store "<name>"`, a wrapper path and an
`epoch N; k of n machines converged` line. That line is the machines' own last
reports, **not** proof; step 6 is the proof.

If it fails: see "Known traps" (login, `dolt` binary, partial state). Re-running
the same command resumes idempotently **[code]**.

## 2. Build the binary

On a build machine, from the merged commit:

```sh
CGO_ENABLED=1 go build -tags gms_pure_go -o /tmp/bd-registry ./cmd/bd
/tmp/bd-registry --version
```

Verify: the printed version/commit is the one you intend to ship. The build tag
is the project default (`BUILD_TAGS` in the Makefile) **[code]**.

## 3. Install it on one machine, together with the pin

Every store wrapper sources `~/.local/bin/.bd-pin.sh` when it exists **[code]**
(`generatedWrapper` in `cmd/bd/brain_registry_shims.go`). On mini0 and mini1 that
file sets `BD_BIN` and `BD_WANT`, and the wrappers refuse to run a bd whose
version differs from `BD_WANT` **[observed]**. The file is generated by the
captain's satellite-config converge scripts (`converge-stores.sh`) **[observed;
that repository is not this one]**. So:

1. Install the new binary and the new `BD_WANT` **in one step** through the
   converge script, not by copying the binary alone. A binary dropped in without
   the pin update makes every wrapper refuse to run, and `bead-doctor` goes red.
2. Keep the previous binary next to it (the convention is `bd.pre-<sha>`) so
   rollback is a rename. The converge script backs up and writes a `restore.sh`
   **[observed]**.
3. On a machine that should not sync at once, hold it: `echo notify >
   ~/.config/brain/registry.policy`; commands then only print `store list changed
   (epoch N -> M): run 'brain stores sync'` **[code]**. Delete the file to go back
   to `auto`.

Verify, on that machine:

```sh
brain --version                     # the new version
<any-store> list                    # a wrapper runs (no pin refusal)
brain stores sync --dry-run         # read the plan before applying
```

## 4. Converge that machine

```sh
brain stores sync
brain stores verify --probe 3
```

Expected: `converged at epoch N (k stores)` from `sync`, `converged` from `verify`
**[code]**. `sync` never rewrites or deletes a wrapper that does not carry the
`# Auto-generated by 'brain stores` marker; such files are reported as "present,
not generated by brain: left alone". It backs up what it replaces to
`~/.local/share/brain/registry-backup/<time>/restore.sh` **[code]**.

Repeat steps 3 and 4 for each machine. Order used so far: host, mini1, MacBook
**[observed]**.

A machine on the **old** build (the MacBook ran `72509161b` on 2026-10-22
**[observed]**) has no `brain stores sync`, no per-store wrapper for stores
created after its build, and so no by-name command for them. Until it has a
build that contains the registry (PR 53) the only route is the host: use
`brain store <name> …` there if that build has it, or run the command on the
host. Do not expect `stores doctor --fleet` to be able to repair it (`fix:` runs
`brain stores sync`, which that build does not have).

## 5. Machines you cannot reach

Some machines (mini2, mini3, lnx) may not be reachable by ssh for the deploy
user **[observed as possible; unverified per machine]**. `doctor --fleet` checks
each machine with `ssh -o BatchMode=yes -o ConnectTimeout=10`, so a machine that
needs a password or a key the deploy user lacks shows as `UNREACHABLE` or
`ASLEEP-OK` and is **not** converged **[code]**. Either fix the ssh access, run
steps 3 and 4 on the machine by hand, or take it out of the roster on purpose
(edit `fleet.yaml`) and say so in your report. Never report a fleet converged
that skipped a machine.

## 6. Prove it: fleet convergence

From the host (or any machine that can ssh to the others):

```sh
brain stores doctor --fleet
```

Expected: one line per machine, e.g. `mini1  CONVERGED  epoch 42, 57/57
wrappers`, then `CONVERGED epoch 42 digest … on 3/3 machines` and exit 0
**[code]**. Read the epoch and wrapper count on every line: all machines must show
the epoch of `brain stores epoch` on the host, and the wrapper count must include
the new store. Exit 1 means not converged (the failing machines are listed with a
`fix:` line), exit 2 means the registry could not be read.

Verdicts: `converged`; `lagging` (applied epoch behind); `drifted` (same epoch but
a wrapper, link or env file missing, or a probe failed); `asleep-ok`
(unreachable but its last report is current); `unreachable` (unreachable and
behind) **[code]**. `lagging` and `drifted` print `brain stores sync --machine
NAME`; run it, then the doctor again.

Finally prove the new store by name on each machine that has a wrapper:

```sh
ssh <machine> '<name> list'
```

## Rollback

Per machine, undo in this order:

1. Put the previous binary back and the previous `.bd-pin.sh` **together**
   (`restore.sh` from the converge backup directory, or rename `bd.pre-<sha>`
   back and restore the old pin file). Binary and pin must match.
2. `brain --version` prints the old version and a wrapper runs.
3. Shims created by `sync` are plain files: restore with
   `sh ~/.local/share/brain/registry-backup/<time>/restore.sh`; links it created
   are symlinks to `rm`.
4. `brain stores poller uninstall` if the poller was installed.
5. To switch the registry off for a command or shell: `BRAIN_REGISTRY=off`
   **[code]**. The tables are additive; nothing is deleted.

Undoing the store itself: `brain stores remove <name>` tombstones it and removes
the generated wrappers on every machine; the data directory, database rows and
prefix stay by design **[code]** (`STORE_REGISTRY.md`).

## Known traps

* **Root login refusal on create.** `Error 1045` / access denied for `root` on
  `brain stores create` means the binary predates PR 55, or the shell lacks the
  configured login. Check `BEADS_DOLT_SERVER_USER`, `BEADS_DOLT_PASSWORD` or the
  credentials file entry for the host:port. Do not weaken the server's root
  account; do not put a password in a ticket or in this repo.
* **Wrong machine.** `create` opens its own SQL connection to the host and port
  in `BEADS_DOLT_SERVER_HOST` / `BEADS_DOLT_SERVER_PORT` (default
  `127.0.0.1:3307`) **[code]**. On a machine that is neither the host nor a
  client it points at nothing useful or at a different server. Run it on the host.
* **Client mode forwards.** A machine with `~/.config/brain/remote.yaml` sends
  commands to its host over ssh before any local code runs. `brain remote`,
  `brain host` and `brain stores sync|verify|poller|shell-hook|doctor --fleet`
  always run locally; a local `BEADS_DIR` that names an existing beads project
  also wins **[code]**. So testing a new binary on a client by running it
  (including from `/tmp/bd-registry`, whatever its file name) can silently run the
  host's binary instead. Set `BRAIN_REMOTE=off` to run it locally once; it is
  also what the host side of every forward sets. The brief for this runbook said a
  name starting with `bd` forwards; the code decides on `remote.yaml` and the
  environment, not on the file name.
* **Version pin.** See step 3. A new binary without the matching `BD_WANT` makes
  every pinned wrapper refuse; the converge scripts own that file, do not edit it
  by hand **[observed]**.
* **`create` output is not proof.** Its `k of n machines converged` line is read
  from reports, which may be old. Only `doctor --fleet` (step 6) proves it.
* **Old build on a machine.** `unknown command "sync"` (or similar) from
  `brain stores sync` means that machine's binary predates the registry. Install
  a newer build first (step 3).
* **`doctor --fleet` runs `brain` over ssh in a non-interactive shell.** The
  default command prepends `~/.local/bin:/opt/homebrew/bin:/usr/local/bin` to
  `PATH` **[code]**; if a machine keeps brain elsewhere, set `command:` for it in
  `fleet.yaml`.
* **Missing `dolt`.** Without the shared-server pins `create` falls back to an
  embedded `dolt init` and needs `dolt` on `PATH` **[code]**; with the `brain`
  wrapper's pins it does not.
* **Half-created store.** A failure after files are written leaves them in place;
  re-run the same command **[code]**. Do not delete `~/data/<name>` by hand.
* **Not adopted.** `note: the shared store registry is not adopted in this
  database` means other machines will never see the store; adopt first
  (`brain stores reconcile`, then `--apply`, per the deploy plan).
