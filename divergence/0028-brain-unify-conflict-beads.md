# Why

The shipped unification build resolved an id held by several stores with a
**winner rule**: one copy kept the id and the other was filed in
`brain_unify_collisions.losing_row`. For 92 of the 123 duplicated ids in the
real federation the copies are byte-identical and that is harmless. For the
other 31 they are the same item at different points in time (24 in content,
7 in bookkeeping columns only), and the shape "one copy lives, the other is a
JSON blob in a side table" hides the divergence from anyone who reads the merged
database as beads.

The captain's decision, recorded in the task that produced this entry: for an id
whose copies differ, **the bead that contains the duplicate becomes a conflict
bead** - "create two new beads, and add their IDs into the conflict bead". This
replaces the winner rule for those ids. It is the model
[`docs/design/brain-collision-duplication-records.md`](../docs/design/brain-collision-duplication-records.md)
(divergence/0025) proposed, with one difference the captain chose: the original
id is not retired as a tombstone, it stays a real bead.

# What changed

- **Conflict beads** (`internal/brainunify/conflict.go`). For an id whose copies
  differ in any column (the same test the build always used):
  - each copy becomes a bead under a minted id,
    `<authoring store's prefix>-<first 12 hex of sha256(original id NUL store)>`
    (design 0025's scheme), carrying that copy's `issues` row and every child
    row it authored, the child rows' scope column pointing at the minted id;
  - the original id stays in `issues` as the **conflict bead**: `open`, a title
    and a description that say it is an unresolved duplicate-id conflict and
    list each copy's minted id, store, status, `updated_at` and title and the
    columns that differ, a `unify-conflict` label, and one `tracks` dependency
    to each copy. `tracks` is bd's existing non-blocking edge (a convoy tracking
    its issues; outside `AffectsReadyWork`): a conflict neither blocks its
    copies nor is hidden by them, and it points from the conflict to the copy.
    `blocks` would make a conflict wait on its own copies, `duplicates` says the
    source is a duplicate *of* the target (a conflict bead is not), and `related`
    is symmetric;
  - links other beads hold to the original id are untouched, so they now reach
    the conflict bead;
  - identical copies are unchanged: one bead, the other copy's rows skipped.
- **Child rows get new keys when the two copies share them.** In the real data
  the brain store's copy of a bead was copied from the other store's, so the
  two copies' `events` and `dependencies` rows carry the **same uuid primary
  keys** (108 shared keys across the 31 ids). Moving both copies' children under
  their minted ids would collide on `events.id` / `dependencies.id` /
  `comments.id`. A table keyed by a single column of its own (not holding the
  scope column) therefore gets a deterministic new key per copy, derived from
  the table, store, original id and old key (a uuid stays a uuid). A table keyed
  any other way is refused before anything is written. This is not in design
  0025, which assumed child rows "move" with a changed `issue_id` alone.
- **One implementation.** `rowMapper` decides what each source row becomes
  (skipped, moved to a copy with its new key, or copied as is). The build's copy
  (`copyMapped`), the replay's reload (`reloadBeadTable`) and the verifier all
  map through it, and the conflict bead's rows are written by one function
  (`tableConflictRows`) used by the build and the replay. The replay deletes
  every id a duplicate's old and new resolution used (the id, the old minted ids
  from the record, the new minted ids from the plan) before reloading, so a
  duplicate that is created, edited, made identical or removed is re-derived
  from the sources.
- **`brain_unify_collisions`** gains `resolution` (`merged-identical` or
  `conflict-bead`), `copy_ids` (JSON `{store: minted id}`) and `copy_hashes`
  (JSON `{store: digest of that copy's rows as they should be in the merged
  database}`). A conflict records no winner and no `losing_row`: nothing is
  skipped. A merged database built before this change lacks the columns; a
  replay refuses it and the answer is one rebuild.
- **`--allow-collisions` is retired.** It guarded the one case where the winner
  rule discarded content; no copy is discarded now, so there is nothing to
  override. The flag is still accepted by `build` and `replay` as a deprecated
  no-op so existing scripts keep running, and is hidden from `--help`.
- **Refusals instead of approximation.** A minted id that two copies derive or
  that an existing bead already has, two copies of one id carrying the same
  non-empty `slug` (the merged database holds slugs unique), a bead table that
  cannot be re-keyed, or a schema lacking the tables a conflict bead needs, all
  refuse the build (and the replay) before the first write.
- **Verifier** (`confirmConflict`, both `--reference recorded` and `live`). The
  aggregate per-namespace fingerprints leave the conflicted ids and the minted
  ids out of both sides (the source side excludes them in every store; the
  merged side excludes the plan's conflict beads and copies), so anything else
  the plan does not name - in particular an extra bead in a minted id's
  namespace - is a fingerprint difference. Each conflict is then checked one id
  at a time: the record names exactly the copies the plan derives; the original
  id is one open issue whose rows, label and `tracks` dependency to each copy
  are exactly the rows the tool authors; nothing else sits at the id but rows of
  stores that hold no copy (counted against the sources); and each copy is one
  `issues` row whose rows in every bead-scoped table equal, by a digest taken in
  Go over rows read the same way on both sides, the source copy put through the
  build's mapper - read from the live sources, or as recorded at build time in
  `copy_hashes`. `exclusionClause` is now NULL-safe (`NULL not in (...)` is
  NULL, which dropped nullable-scope rows from one side of a comparison).

# Acknowledged caveats

- **Beads that block on a conflicted id now block on an open conflict bead.**
  Links to the original id are deliberately kept, so a `blocks` dependency on a
  bead that used to resolve to a closed winner now resolves to an open conflict.
  In the real data 8 inbound `blocks` rows (4 in the brain store, 4 in the task
  store) point at conflicted ids. The `is_blocked` column of those dependents is
  copied from their sources and not recomputed.
- **Stray child rows are carried and counted, not content-compared.** A store
  that holds no copy of a conflicted id but has child rows naming it keeps them
  at the original id; the verifier compares their number with the sources. None
  exist in the real data. Their fingerprint rows are not re-recorded by a replay
  that turns the id into a conflict (only the holders' are).
- **The minted prefix is a policy**: the original id's prefix if the store owns
  it, else a prefix named like the store, else the smallest owned, else the
  original's. A store that owns no prefix (an unregistered database such as
  `db:task`) keeps the original prefix.
- **Hierarchical ids** are not given a positional suffix in the minted id (the
  design assumed they would): none of the 31 is hierarchical, and a flat id is
  parsed to the right namespace by `PrefixOf` either way. A hierarchical
  conflicted id would simply get a flat minted copy.

# Deliberately not done here

A command that resolves a conflict (fold the copies, close one, close the
conflict bead), any UI for conflict beads, and any cutover or write to the
serving machine. Nothing here moves a store.
