# Why

A merged database is built from a moment in the past. A build takes tens of
minutes and the sources are written to throughout and afterwards, so every bead
written, edited, closed or deleted in a source after the build read it exists
only in that source. When the merged database is to become the reference those
changes would be stranded in databases nothing points at. Anyone merging several
databases and then using them while the merge is prepared has this problem; it is
not particular to one migration, so the answer is a general capability of the
`unify` verb family rather than a private script.

# What changed

- **`build` records where it read each source.** A new provenance table,
  `brain_unify_source_commits (store, source_database, commit_hash,
  recorded_at)`, holds each source's newest `dolt_log` commit, read *before* the
  source is copied so a replay's window is a super-set of everything the build
  did not measure. A source whose history head cannot be read, or two stores
  that share one source database, refuse the build. Merged databases built
  before this change have no such table; a replay refuses them and the answer is
  one rebuild.
- **`bd brain unify replay`** (`internal/brainunify/replay.go`). For every
  source it diffs from the recorded commit to the working set to name the
  changed beads (and the changed database-state tables), then reconciles each
  changed bead in the merged database by deleting its rows in every bead-scoped
  table and re-reading them from the sources through the build's own column
  encoding. Inserts, updates and deletes are one operation, a winner that moves
  between stores needs no special case, and the diff's values are never applied.
  Tables Dolt keeps no history for (`dolt_ignore`d, e.g. `wisps`) are reloaded
  whole. It re-records the fingerprints it made stale and advances every store's
  starting commit (read before the diffs, so windows overlap rather than leave a
  gap), all in one transaction followed by a Dolt commit.
- **Duplicated ids reuse the shipped rule.** The sources are planned by
  `Discover` exactly as for a build; the replay applies those collisions and
  writes `brain_unify_collisions` through the function the build writes it with.
  A duplicate that is new, whose decision changed, or whose copies were edited
  and disagree on content is refused without `--allow-collisions`, as in `build`.
  A record whose duplicate went away is deleted.
- **Refusal, not guesses.** Every condition a replay cannot resolve is a
  refusal naming the store and the table (no recorded commits, store joined or
  left, source moved databases, recorded commit gone from a source's history,
  unreadable history, shared source database, a once-populated source table
  gone, a schema the merged database cannot take, content-disagreeing
  duplicates, an insert that clashes). All decisions and reads precede the first
  write and the writes share a transaction, so a refusal leaves the merged
  database as found.
- **`verify --reference live`.** The verifier can recompute the expected side
  from the sources as they stand, with the build's expressions and collision
  exclusions, instead of reading the build's recorded fingerprints. It is the
  acceptance test for a replay: a missed change fails it. The default
  (`recorded`) is unchanged. Collision mismatches are now failed checks in the
  report rather than aborted runs, and a recorded collision no duplicate backs
  any more is a failed check too.
- **Docs.** `docs/brain/MERGING_DATABASES.md` is the user workflow (when to
  rebuild instead of replay, what a replay refuses, the verifier as acceptance
  test, the inherited collision behaviour); the CLI reference pages are
  regenerated.

# Acknowledged caveats

- A live verification of sources still being written can fail for a change made
  between the replay and the check. That is the same failure, answered by
  another replay; quiesce the sources for the verification that gates a cutover.
- The collision plan is computed just before the history is read; a duplicate
  created in that gap is caught by the next verify, not by the replay.
- Only the template store's schema is classified, as in the build. A table that
  exists only in another store is ignored by both.
